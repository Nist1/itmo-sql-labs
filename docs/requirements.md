# Платформа бронирования коворкингов

Платформа для бронирования клиентами рабочих мест и переговорок в коворкингах. Для сотрудников коворкингов есть возможность управлять площадками и расписанием, а администраторам - модерировать систему и формировать отчеты.

## Анализ требований

### Роли пользователей

| Роль | Функционал | Права доступа |
| --- | --- | --- |
| Гость | Просмотр свободных слотов, регистрация | Список коворкингов, тип места, цены, доступность |
| Клиент | Бронирование, отмена, оплата, история бронирования | Статус своих броней, профиль, занятость слотов |
| Сотрудник | Управление площадкой, статус доступности мест, расписание, подтверждение и отклонение броней | Данные о коворкинге, данные клиентов, статусы оплаты броней и т.д. |
| Админ | Модерация, формирование отчетов, блокировка пользователей | Все данные в БД |

### Сценарии использования

**Сценарий 1. Поиск и бронирование**

Роль: Клиент

Шаги: 
1. Выбор коворкинга и даты брони 
2. Просмотр доступных слотов 
3. Выбор места и слота 
4. Оформление брони

Результат: Бронь в статусе **требует подтверждения/подтверждена** в личном кабинете, для других пользователей слот помечается как занятый.

Граничный случай: Два разных клиента пытаются забронировать один слот. Подтвердится должен только один, а второй вернуть ошибку для клиента.

**Сценарий 2. Отмена брони**

Роль: Клиент

Шаги:
1. Клиент открывает бронь в кабинете
2. Нажимает кнопку `"Отменить"`
3. Проверка правил отмены системой или сотрудником

Результат: Бронь в статусе **Отменена**, средства за бронирование возвращаются клиенту, слот освобождается.

**Сценарий 3. Управление расписанием**

Роль: сотрудник

Шаги:
1. Сотрудник открывает панель управления коворкингом
2. Добавляет/удаляет рабочие места
3. Задает часы работы

Результат: Изменения отображаются в системе и становятся видны пользователям, не ломая существующие брони.

Граничный случай: Удаление рабочего места или изменение его расписания с активной бронью должно отменяться с ошибкой, чтобы не сломать брони клиентов без согласования.

**Сценарий 4. Отчет по загрузке**

Роль: Админ

Шаги:
1. Админ выбирает период, за который требуется Отчет
2. Система считает загрузку по коворкингам и типам мест

Результат: Агрегированный отчет по загрузке.

**Сценарий 5. Просмотр истории и деталей своих броней**

Роль: Клиент

Шаги:
1. Клиент открывает историю броней в приложении
2. В списке выставляет необходимые фильтры (активные/завершенные/отмененные)
3. Просматривает детали конкретной брони

Результат: Клиент видит историю своих броней и данные по ним.

**Сценарий 6. Оплата бронирования**

Роль: Клиент

Шаги:
1. Клиент открывает бронь, ожидающую оплаты.
2. Нажимает кнопку оплаты.
3. Система получает результат оплаты.
4. При успешной оплате статус платежа меняется на `оплачен`.

### Сущности и атрибуты

| Сущность | Атрибуты | Предполагаемый ключ | Тип ключа |
| --- | --- | --- | --- |
| user | user_id, email, name, password_hash, role | user_id | суррогатный |
| coworking | coworking_id, name, address, opens_at, closes_at, manager_id (FK) | coworking_id | суррогатный |
| workspace | workspace_id, coworking_id (FK), type, code, capacity, price_per_hour, is_active | workspace_id | суррогатный |
| booking | booking_id, workspace_id (FK), user_id (FK), start_time, end_time, status, created_at | booking_id | суррогатный |
| payment | payment_id, booking_id (FK), amount, status, paid_at, refunded_at | payment_id | суррогатный |

### Связи и кардинальности

`user` 1:N `booking` - У брони всегда должен быть клиент

`user` 1:N `coworking` - Сотрудник может управлять несколькими коворкингами, но у коворкинга только один менеджер

`coworking` 1:N `workspace` - Место всегда принадлежит конкретному коворкингу

`workspace` 1:N `booking` - Бронь всегда создается на конкретное место

`booking` 1:N `payment` - Обязательность со стороны платежа: платеж всегда привязывается к брони (у брони в статусе ожидания может не быть платежа)

### Бизнес-правила и ограничения

1. У каждого пользователя должен быть указан email, и он не должен повторяться. `NOT NULL` и `UNIQUE` в таблице для атрибута
2. Время окончания брони должно быть позже времени начала. `CHECK (end_time > start_time)`
3. Вместимость рабочего места должна быть больше нуля. `CHECK (capacity > 0)`
4. Стоимость часа не может быть отрицательной. `CHECK (price_per_hour >= 0)`
5. Код рабочего места не должен повторяться внутри одного коворкинга. `UNIQUE (coworking_id, code)`
6. Бронь должна ссылаться на существующего клиента и существующее рабочее место. FOREIGN KEY в таблице booking.
7. Платёж должен относиться к существующей брони. FOREIGN KEY в таблице payment.

### Профиль нагрузки

* `OLTP` - Создание/отмена брони, оплата, возврат, вход/регистрация, основные операции по workspace
* `OLAP` - Отчет по загрузке коворкинга за определенный временной период
* Объемы данных: пользователи - тысячи, коворкинги - единицы, рабочие места - сотни, брони - десятки тысяч, платежи - десятки тысяч

### Нефункциональные требования

* Доступность: ~99% uptime. Вначале один инстанс БД, при необходимости - создание реплики
* `RPO` ≈ 5 мин | `RTO` ≈ 30 мин
* Безопасность: гость видит только общую информацию; клиент - только свой профиль, брони и платежи; сотрудник - данные своего коворкинга; администратор - все данные. Пароли хранятся в виде хешей. Проверка прав доступа выполняется приложением перед выдачей или изменением данных.
